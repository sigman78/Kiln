# Diagnostic codes

This is the catalogue of kiln's stable diagnostic codes, the `Kxxxx` numbers that tools and
logs print. It is generated by hand from the enums in `include/kiln/*.h`; the enum is the
source of truth for which codes exist, this file is the source of truth for what they mean.

## 1. What a diagnostic is

A `Diagnostic` (`include/kiln/result.h`) is a small, non-owning record:

| Field | Meaning |
|---|---|
| `code` | Stable numeric id, printed as `Kxxxx`. `0` means "no code" (an ad hoc message with no catalogue entry). |
| `severity` | `Info`, `Warning` or `Error`. |
| `status` | The `Status` (a `Code` plus a detail byte) that the diagnostic accompanies, if any. |
| `asset` | The asset path or id the diagnostic is about. May be empty. |
| `where` | A location within the asset: node, material, section, blob index, and so on. May be empty. |
| `message` | A human-readable, printf-formatted description. |

A diagnostic is not the same thing as a `Status`. `Status` is the 4-byte value every fallible
call returns, cheap enough to propagate through every layer with no allocation. A `Diagnostic`
is the human-readable explanation of *why*, produced only at the point in the code that knows
the details, and delivered to a caller-supplied `DiagSink`. One failure can carry both: the
`Status` for control flow, the `Diagnostic` (with its `Kxxxx` code) for logs and tools. See
`docs/design/error-model.md` for the full error model.

Codes are **stable once released and append only**. A code's number and meaning never change
and are never reused for something else; retiring a check does not free its number. This is
what lets a game team grep their logs for `K4013` across engine versions and get a consistent
answer.

### How tools print a diagnostic

`log_diag_sink()` (`src/core/result.cpp`) is the sink most tools pass around; it forwards each
diagnostic to the log under category `diag`. When `code` is non-zero it formats:

```
K4013 <asset> <where>: <message> (<status name>)
```

For example:

```
K4013 ship_hauler_a.mesh blob 3: table not sorted by encodedOffset or ranges overlap (corrupt)
```

`<asset>` and `<where>` are each omitted (along with their separators) when empty. `<status
name>` is `code_name(status.code)`, the snake_case name of the accompanying `Status` (`corrupt`,
`validation_failed`, `unsupported`, `version_mismatch`, `invalid_argument`, and so on — see
`code_name()` in `include/kiln/result.h`). When `code` is `0`, the leading `K0000`-style prefix
is dropped entirely and the sink prints just `<asset> <where>: <message> (<status name>)`.

| K1021 | `kDiagMeshCookNotBuilt` | Unsupported | Error | `cook_mesh` was called in a `kiln_cook` built with `KILN_MESH=OFF` (a texture-only cook): a `.glb` / `.gltf` source, or a texture embedded in one (`chair.glb#wood`). #### 3.1.1 glTF naming conventions

The codes above refer to naming conventions the importer applies to node and material names.
A node named with the `mount_` prefix becomes an attachment point
rather than visible geometry, so any mesh on it is ignored and its scale is not carried into the
cooked asset (K1010, K1011). A node named `<base>_lodN` (N >= 1) supplies an authored LOD for
the part named `<base>`, and is matched, ordered and gap-compacted by that convention (K1010). A
node named with the `col_` prefix marks a collision-proxy subtree that is excluded from the
cooked mesh entirely. A node named with a bare `_` prefix marks a hidden/utility subtree,
excluded the same way as `col_`. A material name carrying a Blender-style `.NNN` numeric suffix
(e.g. `hull_paint.002`) has that suffix stripped as a duplicate marker, unless stripping it would
collide with another material's name (K1012).

### 3.2 K2000-2999 — Image import and encode

`src/cook/image.cpp`'s pixel operations (`convert_image`, `downsample_2x`, ...) take no
`DiagSink` and never emit diagnostics themselves, but their `InvalidArgument` failures surface
under K2002 when the texture cooker wraps them. Where a code is emitted with more than one
`Status`, both are listed.

| Code | Name | Status | Severity | Meaning | Typical cause / fix |
|---|---|---|---|---|---|
| K2001 | `kDiagImageDecodeFailed` | ParseError | Error | The PNG, JPEG or WebP stream is malformed or truncated: bad signature, missing/truncated PNG IHDR, invalid extent, invalid color type/bit depth, a header/decoder extent mismatch, or a wuffs decode failure not recognized as "unsupported". | Re-export/re-save the image, or re-fetch it if the file is truncated in transit. |
| K2002 | `kDiagImageUnsupported` | Unsupported (a Radiance `.hdr` source with FORMAT=32-bit_rle_xyze or a non-standard orientation, an HDR (f32) source cooked with a usage other than `hdr`, a feature wuffs reports as unsupported, or a WebP source in a build without `KILN_WEBP`), InvalidArgument (the post-decode channel/bit-depth conversion, `convert_image`, rejected the image) | Error | An image feature this build cannot decode (for JPEG: arithmetic coding, 12/16-bit precision, lossless or hierarchical coding), WebP without `KILN_WEBP=ON`, or the conversion to the target channel count/bit depth failed. | Re-export the image as baseline/progressive 8-bit JPEG or as PNG; for WebP, configure with `-DKILN_WEBP=ON`. |
| K2003 | `kDiagImageUnknownFormat` | Unsupported | Error | The source bytes start with no PNG, JPEG, WebP or KTX2 signature. The decoder is chosen by signature, never by file extension or glTF `mimeType`. | Supply a PNG, JPEG, WebP or KTX2 file; check the asset was not corrupted or mislabeled. |

| K2005 | `kDiagImageDownscaled` | kOk | Info | The source image exceeds the resolved size cap (settings `maxSize` and/or the target's cap); the top mip level(s) were dropped before building the chain. | Informational. | K2006 | `kDiagImageNpotMips` | kOk | Info | A non-power-of-two image is building a mip chain; levels use floor halving instead of exact halving. | Informational. Use power-of-two dimensions if exact mip alignment matters. |

### 3.6 K5000-5999 — Runtime and store

Source: `kiln::RuntimeDiagCode` in `include/kiln/assets.h`. Emitted by the runtime context, request
and pump machinery (`src/runtime/context.cpp`, `registry.cpp`, `loader.cpp`, `pump.cpp`,
`register.cpp`, `watch.cpp`). K5014-K5016 are a separate enum, `kiln::cook::ProviderDiagCode` in
`include/kiln/cook/provider.h`: the cook provider emits them, and the runtime folds them into
K5002 like the cooker's own K1xxx-K3xxx diagnostics (see the note below the table). Unlike the
cook-side ranges, most of these are produced on a worker thread
(`loader.cpp`) but only *delivered* to the host's `DiagSink` from `pump()`: a worker only fills in
`Slot::jobDiag`/`jobStatus` and a short capture buffer (`DiagCapture`); `pump()`'s `fail_slot()` is
what actually calls `diagf()`. All codes in this range are `Severity::Error` except K5006, K5011
and K5012 (`Warning`); K5007 is delivered as a panic message, not a `Diagnostic` (see its row), and K5009 can
also panic instead of reaching the `DiagSink` in one sub-case (see its row).

| Code | Name | Status | Severity | Meaning | Typical cause / fix |
|---|---|---|---|---|---|
| K5001 | `kDiagStoreMiss` | NotFound | Error | No cooked file exists for the asset and no cook provider is installed, or a cook provider is installed but found no source to cook. | Cook the asset into the store ahead of time, install a `kiln::cook::CookProvider` with a root that has it, or fix the asset path. |
| K5002 | `kDiagCookOnMissFailed` | Whatever the cook provider returned (not `NotFound`, which is K5001 instead) | Error | The installed cook provider was asked to produce the asset and returned an error. | K5003 | `kDiagAssetLoadFailed` | Varies: `InvalidArgument` (a valid name's asset id hashes into the reserved placeholder range 0..15, rejected at `request_*`/`register_*` time before any IO — an invalid name itself is rejected earlier as K5013), or the `Status` the IO backend / `.mesh`/KTX2 reader returned (e.g. `IoEof`, `Corrupt`, `ValidationFailed`, `VersionMismatch`) for a failure while opening or reading the asset. | Error | Catch-all for "the load itself failed": a name that hashes into the reserved placeholder id range 0..15, or an IO/validation failure reading the store file, registered bytes, or cook-provider output. `kDiagCookOnMissFailed` (K5002) and `kDiagAssetLoadFailed` (K5003) are the two codes that can carry
a nested diagnostic: the worker-side reader (`.mesh`/KTX2, K4xxx) or cook provider (K1xxx-K3xxx, or
its own `ProviderDiagCode` K5014-K5016) that actually detected the problem writes into the slot's
`DiagCapture` (first diagnostic only,
preferring the first `Error`); `pump()`'s `fail_slot()` formats that captured text into the K5002/
K5003 message it emits, so only one diagnostic per failed load reaches the host's `DiagSink`, not
one per underlying check. See open-questions R5f for the open point (a thread-safe sink that could
deliver every worker-side diagnostic instead of only the first).

`store_write()` (`src/cook/store.cpp`, the cook-side store writer used by `kiln-cook` and
`kiln::cook::install_provider`'s disk mode) predates this range and is unchanged by M3: it still
reports failures through the same `Diagnostic`/`DiagSink` machinery but with no catalogue code — it
emits code `0` (no catalogue entry, printed without the `Kxxxx` prefix) at `Severity::Error`, with
`Status` `IoError` for filesystem failures (`mkdir`/`fopen`/write/rename, detail = errno) or
`InvalidArgument` for a path that does not fit the function's fixed-size buffers. Moving it onto a
real K5xxx code is still open.

## 4. Adding a code

1. Pick the next free number in the owning range (see §2). Never reuse or renumber an existing
   code, even one that later becomes dead code; once released, a code's meaning is permanent.
2. Add it to the `DiagCode` enum in the module's public header (for example
   `include/kiln/mesh.h` or `include/kiln/ktx2.h`), with a one-line doc comment.
3. Add a row to the matching table in this file, in the same change. This file and the enum
   must never drift apart: a code with no row here, or a row with no enum entry, is a bug.
4. Write tests (and any other code) against the enum name (`kiln::mesh::kDiagBlobTable`), never
   against the bare number (`4013`). The number is for logs and artists; the name is for code.
